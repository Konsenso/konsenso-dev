---
title: Testing AI before you ship it
description: "A developer's introduction to stress-testing AI systems before deployment, starting with the two core practices: red teaming and evals."
---

You've shipped software before. AI features break the habits you built doing
it: the same input can produce a different output twice, the behaviour lives in
weights you can't read, and a determined user can *talk* the system into doing
things no one wrote code for. Testing an AI feature before you deploy it is a
different discipline from testing ordinary software, and this page is the
introduction to it.

It's written for the person who's been handed an AI feature and a launch date:
developers, platform teams, and security engineers who need to know whether the
thing is safe to ship, and be able to show *why*.

Two practices do most of the work, and mature teams do both. Red teaming finds
the problems. Evals tell you whether they're getting better or worse.

## What is AI red teaming

Red teaming is open-ended and adversarial. You, or a tool acting for you,
actively try to break the system: generating and mutating attacks to find the
failure you didn't know to look for. It's an attacker's mindset applied on
purpose, before a real attacker gets there.

In practice that means things like prompt injection (untrusted text hijacking
your instructions), jailbreaks (coaxing the model past its own refusals), and
getting it to leak data or the system prompt it was supposed to protect.

Red teaming is good at surfacing unknown unknowns. What it can't give you is a
single number, because it's exploratory by nature. That's the job of the second
practice.

## What are AI evals

An eval is fixed and repeatable. You run a defined set of prompts and measure
the result: an attack-success rate, an accuracy, a refusal rate. Because the set
is fixed, you can run it again on every change and watch the number move.

That makes evals the thing you gate a release on. Run them in CI, set a
threshold, and a regression fails the build the same way a broken unit test
would.

The tradeoff is that an eval only tests what's in the set, so it won't find a
new failure on its own. That's why the two go together: red teaming finds what
to worry about, and an eval turns it into something you can track release over
release.
